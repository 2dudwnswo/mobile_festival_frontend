# 축제 주점 관리자 앱 (Android · Kotlin)

> **개발 안전장치:** debug는 기본 Firebase 에뮬레이터이며 운영 DB에 접속하지 않습니다.
> 테스트 방법은 [firebase/README.md](firebase/README.md)를 따르세요. 운영 접속은 3단계 별도 승인 후에만 합니다.
> 이 저장소의 규칙은 에뮬레이터 전용입니다. **firebase deploy 금지**. 아래 과거 설계 설명은 v2와 다를 수 있으며 전체 문서 정리는 4단계에서 진행합니다.

```
mobile_festival_frontend/
├─ android/          ← 관리자 앱 (Android Studio로 열기)
├─ firebase/         ← Firestore 보안 규칙·색인·에뮬레이터 설정, 규칙 테스트
├─ docs/FIREBASE.md  ← 친구와 맞출 Firebase 데이터 설계 (계약서)
├─ docs/API.md       ← (구버전) 노트북 서버 방식 명세 — 참고용
└─ mock-server/      ← (구버전) 노트북 서버 방식 테스트 서버 — 참고용
```

데이터는 **Firebase(Firestore)**로 주고받습니다. 스태프 폰은 핫스팟 폰의 모바일 데이터로 인터넷에 연결합니다.

## 1. Firebase 준비 (처음 한 번, 운영자)

### 1-1. google-services.json 받기 (없으면 앱 빌드가 실패합니다)
1. [Firebase 콘솔](https://console.firebase.google.com) → 친구와 같이 쓰는 프로젝트 선택
2. ⚙ **프로젝트 설정 → 일반 → 내 앱**에서 Android 앱 추가 (이미 있으면 그 앱 선택)
   - Android 패키지 이름: **`com.festivalpub.admin`**
3. **google-services.json 다운로드** → `android/app/google-services.json` 에 넣기
   - 이 파일은 **git 에 올리지 않습니다** (`.gitignore` 에 등록됨). 새 PC에서 빌드할 때마다 다시 받아 넣습니다.
   - 저장소를 받은 직후에 들어 있는 파일은 없습니다. 개발 PC에 `demo-festival-pub`(가짜 프로젝트)용 파일이 있다면 에뮬레이터 테스트 전용이니 실제 파일로 덮어씁니다.

### 1-2. 스태프 공용 계정 만들기
1. 콘솔 → **Authentication → 로그인 방법 → 이메일/비밀번호** 사용 설정
2. **Authentication → 사용자 → 사용자 추가**
   - 이메일: **`staff@festival-pub.local`** (앱과 보안 규칙에 이 주소가 들어 있습니다)
   - 비밀번호: 스태프끼리만 공유할 비밀번호 (코드·git·단톡방 공지에 남기지 말고 현장에서 알려 주세요)
3. 폰마다 앱 첫 화면에서 이 비밀번호를 **한 번만** 입력하면 로그인이 유지됩니다. 설정 ⚙ → [로그아웃]으로 해제합니다.
   - 비밀번호가 샜다면 콘솔에서 바꾸면 되고, 그러면 모든 폰에서 다시 입력해야 합니다.

### 1-3. 보안 규칙·색인 — 배포 금지

운영 규칙은 동현이 관리합니다. 이 저장소에서는 로컬 에뮬레이터 테스트만 실행합니다.
[2단계 로컬 검증 안내](firebase/README.md)를 참고하세요.

## 2. 앱 실행

1. Android Studio(최신 버전)에서 `android` 폴더 열기 → Gradle 동기화가 끝날 때까지 대기
2. 폰에서 개발자 옵션 → USB 디버깅 켜고 연결 → ▶ Run
3. 스태프 폰에 배포할 APK: 메뉴 **Build → Build APK(s)** → `app/build/outputs/apk/debug/app-debug.apk` 를 카톡/USB로 전달해서 설치

첫 실행 시 **알림 권한·전화 권한 허용** → 공용 비밀번호 입력(처음 한 번) → 담당자 선택.
웨이팅 맨 위 팀을 탭하면 확인 없이 바로 발신됩니다.

## 3. 화면 구성

| 탭 / 화면 | 기능 |
|---|---|
| 1-O 로그인·담당자 | 스태프 공용 비밀번호(폰마다 처음 한 번), Firebase 연결 상태, 담당자 선택(앱 실행할 때마다) |
| 1-1 테이블 | 서버에서 받은 가로×세로 격자를 한 화면에 표시, 색상(빈자리/이용중/임박/초과), 남은 시간 |
| 1-2 테이블 상세 | 빈자리: 웨이팅 팀 배정 또는 현장 손님 착석 → **착석 순간 100분 타이머 시작**. 이용중: 연장 +10/20/30, 주문 내역과 주문 합계(입금확인된 주문만), 이용 종료 |
| 1-3 웨이팅 | VIP(번호 V1, V2…) 맨 위, 일반은 등록순. **맨 위 팀 탭하면 바로 전화**, 호출 후 3분이 지나면 [무응답] 버튼. 무응답 팀은 아래쪽에 흐리게 표시 |
| 1-4 웨이팅 상세 | 전화, 빈 테이블 번호 눌러 착석 배정, 무응답 처리, 대기 복귀, 취소 |
| VIP 등록 | 웨이팅 탭 우측 하단 버튼 |
| 1-5 주문 입력 | QR 주문의 예비 수단. 테이블 → 메뉴 → 수량 → 전송(확인창). 직원 주문도 QR 주문처럼 서버가 입금을 확인해야 주방으로 감 |
| 1-6 주방 | **서버가 입금확인한 주문만** 입금 순서대로. 새 주문이 들어오면 짧은 알림음. 15분 넘으면 빨간색. 조리완료(확인창, 되돌릴 수 없음) |
| 1-S 설정 (⚙) | 테이블 배치 보기(서버에서 관리, 앱에서는 수정 불가), 회전/임박/무응답 시간, 담당자 변경, 계정 로그아웃 |

알림: 테이블이 초과되면 진동+소리+"N번 테이블 시간 초과" 알림(앱이 백그라운드여도), 정리될 때까지 1분마다 반복. 임박이 되면 짧은 진동 1회.
인터넷이 끊기면 빨간 배너가 뜨고, 호출·조리완료 같은 변경은 쌓였다가 연결되면 자동 전송됩니다("전송 대기 n건"). 착석·이용 종료·VIP 등록·직원 주문은 끊긴 동안 저장되지 않으니 종이에 적어 두었다가 복구 후 입력하세요.
화면은 행사 중 꺼지지 않도록 설정되어 있습니다.

## 4. 반영된 결정 사항

- 회전 100분, 타이머는 **착석 순간** 시작 (결제와 무관)
- 주문은 테이블 QR로 받고, **주문마다 선결제** → **입금확인은 서버가 판단**하고, 앱에는 입금확인된 주문만 나타남 (앱은 입금확인·주문취소를 하지 않음)
- 빈 테이블에서 들어온 QR 주문은 서버가 거절
- VIP는 일반 손님 "내 앞 대기" 계산에서 제외 (순번이 뒤로 밀리지 않음)
- 무응답: 호출 후 3분이 지나면 스태프가 수동 처리, 늦게 오면 원래 순서로 복귀
- 테이블 배치(가로×세로, 개수)는 서버 쪽에서 관리하고, 앱은 받아서 보여주기만 함
- 테이블 번호는 1번부터 고정 (QR 번호와 같음)
- 데이터는 Firebase(Firestore). 앱은 스태프 공용 계정으로 로그인, VIP는 앱 전용 컬렉션(`vipWaitings`)
